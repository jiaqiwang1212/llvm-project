# MLIR：在机器学习框架图算法中的渐进式应用

现有的 MLIR 文档聚焦于长远愿景、各模块如何协同配合，以及在遥远未来模块化、可组合基础设施所能带来的收益。这一视角固然对一些人颇具吸引力，但对于那些更关注"当下"的人来说却令人担忧——当每个具体问题都可以就地修复时，为何要进行一次"革命性"的变革？

本文解释了采用 MLIR 来解决基于图的问题*并非*一场革命性的变革：它是一系列渐进的步骤，每一步都相互积累，并在过程中持续交付局部价值。本文还针对一些反复出现的困惑点进行了解答。

一点说明：尽管 MLIR 的一大优势在于它能够覆盖从图算法到低层级代码生成的完整范围，但本文聚焦于 MLIR 在**图层级算法**中的应用。MLIR 同样将解锁令人兴奋的代码生成机会（特别是考虑到其集成最先进多面体技术的创新方式），但涉及 MLIR 与 XLA、Eigen 等关系的话题，不在本文讨论范围之内。

本文以 TensorFlow 为例，因为它是我们当前工作的重心，但我们相信，同样的视角对于其他可能在未来考虑采用 MLIR 的机器学习框架的开发者也同样适用。

### MLIR 有何意义？

MLIR 是一个重载的缩写，展开为"多层次中间表示"（Multi-Level Intermediate Representation）。其高层目的是提供一种以灵活方式描述和变换程序与计算的机制。它为常量折叠、死代码消除、图重写等提供了通用编译器基础设施，这些基础设施与特定方言所选择的表示方式（如其并发语义）无关。它在构建时特别注重编译时间和内存效率、源位置信息的精确传播（对于报告高质量错误和警告至关重要），并以可测试性为设计目标。

TensorFlow 拥有众多子系统（其中一些是专有的，例如 Tensor-RT、nGraph、CoreML 等），以及这些不同子系统之间的翻译层，而这些翻译层面临着类似的挑战。（顺带一提，这些子系统各自的内部实现往往也能从 MLIR 基础设施中受益，但这不是本文的关注点。）

MLIR 的一个关键洞察是：这些子系统通常同时具备两方面特性：它们既是特定的数据结构和编码（例如 HLO 图、TF-Lite 的 flat buffer 格式、TensorFlow 的 Graph 格式、ONNX 抽象等），也是计算的抽象（对卷积的特定建模方式、一组支持的操作等）。

MLIR 使用标准 IR（即一组数据结构）来表示这些计算——这使得跨问题领域共享大量基础设施成为可能。MLIR 随后允许定义特定领域的"方言"，用于描述在给定应用中合法且受支持的操作集合。这意味着数据结构之间的实际翻译被保持得尽可能简单——从而相对容易地保证"正确性"。这使得通用编译器基础设施能够处理映射问题以及领域内的其他问题。

MLIR 的设计直接汲取了构建（并长期维护）LLVM IR、LLVM SelectionDAG、LLVM 机器指令表示、Swift SIL IR 等中间表示的经验，同时从 TensorFlow、XLA HLO 中汲取新的教训，并从在其之上构建无数研究和生产系统的实践中持续学习。我们的目标是推动编译器领域技术水平的整体进步，而不仅仅是将一些成熟技术应用于机器学习领域。

### 采用意味着什么？

本文的重点并非鼓励重写 TensorFlow 中的任何特定子系统——事实上，为重写进行辩护的门槛很高，且往往高度依赖于具体子系统的情况。尽管如此，有几个子系统无论如何都即将被重写或进行实质性修改，因此我们以这些子系统为例，具体描述 MLIR 在这些情况下所提供的收益以及所需的付出。所讨论的子系统包括：

1.  TF Lite TOCO 翻译器，我们需要改善其错误报告/可靠性问题，并将其泛化以支持更多的操作；
1.  TF/XLA 桥接层，需要通过合并其部分使用模型来改善可用性，支持动态形状，并将对 Tensor-RT 和 nGraph 的访客子系统支持泛化。
1.  Grappler 是另一个在未来可能进行大幅修改的子系统，从 MLIR 框架中肯定会受益，但目前尚无已知的工作计划，因此我们不再进一步讨论。

为这些工作采用 MLIR 的方式是相同的——事实上，支持 TF Lite 的工作在很大程度上是支持 TF/XLA 桥接层功能这项更大工作的子集。TF Lite 和 TF/XLA 桥接层包含若干编译器 pass（例如封装、函数化控制流、操作降低、融合、常量折叠、形状推断等）。

MLIR 支持从 TensorFlow Graph 转换到 MLIR 并再转换回来，这意味着我们可以从在流水线中插入一个空操作（no-op）的 MLIR 来回翻译开始，验证没有任何功能被破坏。然后我们可以逐一替换编译器变换，通过重新实现它们（采用我们正在规划的改进算法）来完成迁移。

这是一个开发计划，我们实际上不会发布一个只为单个 pass 使用 MLIR 的 TensorFlow 版本。在实践中，我们会在一个选项后面对 MLIR 功能进行门控，针对整个子系统（例如 TOCO 翻译器）构建替代方案，当时机成熟时，我们将进行 A/B 比较，并最终完成切换，随着时间的推移逐步淘汰旧代码。

## MLIR 提供了哪些收益？

上述采用计划听起来可能在短期内只会让事情变得更糟——我们对同一功能有了两套实现，分散了精力，等等。要使这一切值得，我们应当有充分的理由相信，我们正在朝着一个更好的未来构建，当它落地时，会让客户和 TensorFlow 工程师感到更满意。以下我们不分先后地描述 MLIR 所提供的几项收益：

### 无损的人类可编辑文本表示

MLIR 的内存数据结构具有人类可读可写的格式，以及该格式的[规范说明](../LangRef.md)——就像任何其他编程语言一样构建。该格式的重要特性是：紧凑、易于阅读且无损。你可以将 MLIR 程序转储到磁盘上进行修改，然后再通过若干 pass 进行处理。

如果你没有在使用这种方式工作的系统上有过经验，很难高估这在实践中的重要性：这意味着你可以在 IR 对象上调用 `foo->dump()` 来查看其完整内容，意味着你可以对比变更前后的 IR 差异，对 IR 文件进行增量规约，以及许多其他操作。

### 图校验 Pass

与许多其他流行的编译器基础设施一样，MLIR 为"校验器"提供了基础设施和实现，用于检查 IR 是否格式正确。MLIR 校验器是一个简单的框架，使得为这些正确性属性提供单一事实来源变得容易，并且跨所有方言（例如 TF Graph、TF Lite flat buffer、XLA HLO 等）都是通用的。

校验器 pass 有点像一个"超级断言"，能够在程序变换中早期捕获错误，使工程师更高效、产品更可靠，并在问题出现时更容易追踪——因为校验器可以随时运行，既可作为编译器 pass 运行，也可通过单个函数调用执行。

虽然 MLIR 为 IR 校验提供了经过深思熟虑的基础设施，并对现有 TensorFlow 操作进行了简单检查，但这里仍有很多需要补充的地方，也有大量参与贡献的机会！

### 以可测试性为设计目标

MLIR 在这方面有很多体现，但我们将聚焦于编译器变换，因为它们最容易理解。编译器变换被建模为 `Pass` C++ 类的子类，由 `mlir-opt` 工具驱动。结合无损文本表示，为编译器变换编写单元测试变得非常容易。例如，下面是一个简单的测试，展示了"x-x"被转换为零：

```mlir
  // RUN: mlir-opt %s -canonicalize | FileCheck %s
  func.func @test_subi_zero_cfg(%arg0: i32) -> i32 {
    %y = arith.subi %arg0, %arg0 : i32
    return %y: i32
  }
  // CHECK-LABEL: func @test_subi_zero_cfg(%arg0: i32)
  // CHECK-NEXT: %c0_i32 = arith.constant 0 : i32
  // CHECK-NEXT: return %c0
```

"CHECK" 注释由 [LLVM FileCheck 工具](https://llvm.org/docs/CommandGuide/FileCheck.html)解释，它有点像功能极为强大的 grep。该测试完全自包含：它将输入送入[规范化 pass](../Canonicalization.md)，并检查输出是否与 CHECK 行匹配。更多示例请参见 `test/Transforms` 目录。相比之下，标准单元测试将底层框架的 API 暴露给大量测试（使重构和迁移 API 变得更困难），通常需要更多代码，并加剧了链接时间的问题。相关示例请参见 [TensorFlow 测试套件中的 TEST_F 函数](https://github.com/tensorflow/tensorflow/blob/master/tensorflow/core/grappler/optimizers/arithmetic_optimizer_test.cc)。

MLIR 在设计上全面贯彻了这种可测试性，使我们能够形成一种文化：期望每一个改变行为的提交都包含一个测试用例，并且这些测试用例随着时间的推移保持稳定可靠，因为它们测试的恰恰是应当测试的内容。当然，端到端集成测试对于某些方面仍然非常有用！

### 警告、错误诊断与位置追踪基础设施

MLIR 受益于构建其他编译器所积累的经验教训——包括 Clang，它[[树立了标准](http://blog.llvm.org/2010/04/amazing-feats-of-clang-error-recovery.html)](http://blog.llvm.org/2010/04/amazing-feats-of-clang-error-recovery.html)，在 C/C++ 编译器诊断的实现质量方面引领了行业。借鉴这些经验（并修正 LLVM 中的缺陷），MLIR 要求操作和函数携带抽象的位置信息，变换必须传播这些信息，并提供标准化机制来发出错误和警告，以及供客户端挂接以便以自定义方式捕获和报告它们。

为什么这很重要？在实践中，许多图到图的翻译器可能会失败（例如 TF Lite 在使用不支持的操作时），能够以尽可能精确的方式将错误向上报告给用户非常重要，这样才能让用户知道如何采取行动。这包括追踪通过操作融合和分裂进行的重写、映射回语言/API 特定的领域等。

对于基础设施开发者来说，这更是一大福音，因为这意味着为此编写良好的测试非常容易：MLIR 的测试工具会捕获 pass 产生的诊断信息（使用标准诊断挂钩），并检查它们是否与测试用例中的预期诊断匹配。例如，为了测试代码生成器中的依赖分析基础设施，Andy Davis 编写了一个简单的 pass，用于检查依赖关系并将其作为"note"发出，使他能够编写如下测试：

```mlir
  // RUN: mlir-opt %s -memref-dependence-check -verify-diagnostics
  func.func @different_memrefs() {
    %m.a = memref.alloc() : memref<100xf32>
    %m.b = memref.alloc() : memref<100xf32>
    %c0 = arith.constant 0 : index
    %c1 = arith.constant 1.0 : f32
    memref.store %c1, %m.a[%c0] : memref<100xf32>
    // expected-note@-1 {{dependence from memref access 0 to access 1 = false}}
    %v0 = memref.load %m.b[%c0] : memref<100xf32>
    return
  }
```

请注意，这里有一个重大限制：MLIR 存在"垃圾进、垃圾出"的问题：如果输入到 MLIR 的位置信息不精确，那么 MLIR 也无能为力。TensorFlow/Python 方面正在开展改善这一情况的工作，而 Swift for TensorFlow 由于其设计已经具备了完美的位置追踪。

### IR 中捕获的形状信息

在 TensorFlow Graph 中，每个操作使用非常简单的类型系统（TF_DataType）接受和返回值，其中每个值都是一个秩和维度未知的张量。与此同时，许多图在大范围的计算中具有静态可知的形状，即使是动态形状的操作也往往具有静态可知的维度。许多分析和变换在可用时会受益于并使用这些信息，但由于 TensorFlow 图不捕获这些信息（例如不将其序列化到 proto），pass 不得不按需使用 ShapeRefiner 重新计算。

[MLIR 张量类型](../Dialects/Builtin.md/#rankedtensortype)直接捕获形状信息，因此你可以有如下内容：

```mlir
  %x = tf.Add %x, %y : tensor<128 x 8 x ? x f32>
```

在 IR 中捕获这些信息预计能加速变换（避免反复重新计算相同的信息），从而使应用更强的形状分析算法成为可能。这也使得处理 IR 变得更容易，因为旁路表示可能会过时，并且从人体工学角度来看 API 也更易于使用。

### 统一的图重写基础设施

这仍然是一个正在进行中的工作，但我们对于一个[通用重写基础设施](RationaleGenericDAGRewriter.md)有了清晰的愿景，用于使用声明式模式格式将 DAG 块转换为其他 DAG 块。DAG 到 DAG 重写是许多常见编译器优化、降低和其他重写的通用解决方案，拥有一个 IR 使我们能够投入构建单一高质量实现。

声明式模式规则相比命令式 C++ 代码有许多优势：它们更紧凑、更易于推理、可以针对其编写检查器，并且可以构建新工具以有趣的方式检查和操作声明式模式——例如将定理证明器应用于其上。随着基础设施的成熟，看到这个生态系统的发展将令人兴奋。

### TensorFlow 操作语义的明确化

处理 TensorFlow 时的一大挑战是，在操作图时需要保留和了解许多不变量和行为，这些可能难以推理并会导致错误。诸如"死值"、Switch 和 Merge 节点、并发语义、即使传入死值也会执行的节点、多设备程序表示等……所有这些都增加了复杂性，使得推理某个变换或分析是否在一般情况下正确变得充满挑战。即使是像常量折叠或将整数 `x-x` 转换为 `0` 这样简单的事情也非同小可，因为你需要考虑控制依赖边。

我们针对 MLIR TensorFlow 方言的主要目标之一，是理清这些情况，并将现有的 TensorFlow 图升级到更易于推理的语义。解决这些问题的方案仍在讨论中，但这些讨论已经产生了大量潜在答案：为 switch/merge 引入 `tf_dead_or<x>` 类型、使用 futures/async 语义对 TF 操作进行建模等。这些具体问题对于 MLIR 的成功都不是至关重要的（由于其"元"性质，任何给定方言的抽象决策都由其自身决定），但每一个解决的问题都会使处理和变换 TensorFlow 操作变得更容易。我们预计当 MLIR 工作超越 TF Lite/TOCO 支持阶段后，这些问题将在接下来的几个月内得到明确。目前正在进行的讨论非常有价值，并且正在取得进展。

### 人体工学

一个理论上次要但实践中重要的点是：MLIR 的设计使得代码变换比其他系统更容易、更节省内存、更不易出错。`TensorFlow::Graph` 存在实现问题，其中相同的信息在不同地方以冗余方式存储（必须手动保持同步），对某些构造有些不寻常的表示（例如函数库，这使得添加或删除函数非常困难，例如在过程间变换期间），并且在图中存储了执行器使用的信息，但这些信息对于程序变换来说并非必要。

TensorFlow 多年来在这方面取得了很大进展，关于未来进一步改进也有很多想法，我们很高兴 MLIR 今天就能满足这些需求（使实现正确的程序变换变得更容易），并致力于努力推动其进一步改进。

### 编译时性能和内存使用

MLIR 在算法和数据结构上被设计为内存和编译时高效，使用不可变和唯一化的结构、低级位压缩以及其他成熟技术，避免不必要的堆分配，并支持 MLIR 程序的简单且安全的多线程优化。还有其他理由相信，常见变换的 MLIR 实现将比 Python 和 C++ TensorFlow::Graph 实现更高效，这取决于 TensorFlow 当前的实现细节。

也就是说，这在目前在很大程度上还只是理论。当各子系统的新实现可用时，我们将观察实践中发生什么：届时就没有必要推测了——我们可以进行测量。

## 常见问题与疑虑

这里我们解答一些常见问题和疑虑。

### MLIR 是不是一个很大的依赖项？

我们听说至少有一些人担心 MLIR 是一个"大"依赖项，可能导致较大的代码体积。以下是关于 MLIR 的几个要点：

1.  就绝对量而言，整个 MLIR 代码库是一个相当小的 C++ 代码库，与现代机器学习框架的规模相比更是如此。
1.  与 LLVM 一样，MLIR 被设计为一组库，客户端可以根据需要链接或忽略。例如，MLIR 中的变换与核心 IR 抽象保持分离，方言特定的代码（例如 TensorFlow、TF-Lite、XLA 等）均可由构建系统独立选择。不关心 XLA 的客户端不会链接该代码，无论它们是 TF-Lite 系统还是与 TensorFlow 完全无关的客户端。
1.  MLIR 唯一的第三方依赖是 LLVM，但它不依赖于 LLVM IR 或任何其他繁重的依赖——它仅依赖于 LLVM 的支持库，该库提供了高效的哈希表和其他 [STL 所不具备的内存高效数据结构](http://llvm.org/docs/ProgrammersManual.html#picking-the-right-data-structure-for-a-task)。有人讨论过将这组库单独拆分为 LLVM 中的一个子项目，供 LLVM IR 项目依赖。这对 MLIR 以及其他 LLVM 子项目来说都将是一件好事。
1.  TensorFlow 和许多其他框架已经使用了 LLVM——如果是这种情况，MLIR 根本不会引入额外的依赖项。

### MLIR 如何在 TensorFlow 中表示{控制流、并发、…}语义？

MLIR 提供了一种方言，它是 TensorFlow 图与 MLIR 之间的同构一对一映射，以及相当完整的双向翻译器（唯一已知的差距是有几个 TF_DataType 枚举尚未处理）。MLIR 是"多层次 IR"，允许它以不同的抽象层次表示代码，因此能够以完全向后兼容的方式忠实地表示 TensorFlow 代码（即使存在一些历史遗留问题！）至关重要。

*除了*同构映射之外，我们正积极致力于提升在 MLIR 中处理 TensorFlow 图的抽象层次。这样做将使编写 TensorFlow 变换比今天更容易，并将提供一条将 TF 1.x 图迁移到 TF 2.x 世界的路径。例如，由于 MLIR 具有可扩展的类型系统，我们可以直接建模某个张量值是否不可能是"死"值——类似于现代编程语言中 optional 类型的使用。

这些讨论有时会造成混淆，因为有几个问题被混为一谈：

*   TensorFlow 图的当前语义是什么，我们可以依赖哪些不变量？
*   TensorFlow 2.0 中的语义应该是什么？
*   程序在实践中依赖什么，如果它不友好，我们能否迁移它？
*   我们能否找到一种方式，让变换不必担心 Switch/Merge 的复杂性，通过使用更高层次的控制流表示？（初步答案：可以）
*   MLIR 应该如何表示异步与同步操作，提供哪些不变量，这与控制流如何衔接？
*   何时执行可能减少并行性的优化是安全且有益的？

所有这些问题都有一个"保守/安全的后备方案"：我们可以继续提供与 TensorFlow 历来相同的抽象。也就是说，我们正努力提升表示层次（利用 MLIR 的"多层次"特性），因为这样做将使编写分析和变换比当前在 TensorFlow 中容易得多。

### 非目标

重要的是要指出 MLIR 不打算做的事情。例如，MLIR 没有运行时组件：TensorFlow 执行器、TF Lite FlatBuffer 解释器或其他现有运行时应按原样使用。

另一个非目标是：MLIR 目前不支持稳定的二进制编码。我们肯定会在某个时候添加这一功能，但在此之前，现有格式应用于序列化和分发。
