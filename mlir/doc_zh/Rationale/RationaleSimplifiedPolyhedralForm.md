# MLIR：简化多面体形式的理由

MLIR 采用多面体编译器技术，因为它在表示和变换稠密数值核心方面具有诸多优势，但它使用的形式与其他多面体框架有显著差异。

**免责声明 / 警告**

本文是一份非常早期的设计提案（此后已被接受），探讨了使用这种简化形式相对于传统多面体调度列表形式的权衡取舍。在某个时间点，本文可以被整理并写成一篇正式的学术论文，但在此之前，以这种粗糙的形式包含在此处比完全不包含要好。请注意，本文使用了古老的语法，不应被视为现代 MLIR 的规范参考。

## 介绍

本文讨论了项目的总体目标，介绍了背景和两种备选方案，然后讨论了这些设计的权衡取舍。作者：Chris Lattner。

## IR 的一般目标，以及 mlfunc 的具体目标

我们目前计划的 MLIR 表示由两种函数组成：一种类似 LLVM 的"CFG 函数"和一种"ML 函数"：以多维循环形式表示的函数。其思路是，CFG 函数能够完全通用地表达任意计算，但不便于循环变换。相比之下，mlfunc 有限制（例如限于涉及仿射空间上循环嵌套的控制流），但这些限制使其更容易进行变换和分析，特别是对于机器学习核心中的那类计算。

中间表示的设计是一个优化问题，它做出有意为之的权衡，旨在使某些类型的编译器变换变得简单。毕竟，在任何 IR 上进行几乎任何变换在理论上都是"可能的"：从理论上讲，我们甚至可以在汇编语言上进行循环变换。但这类变换需要太长的时间来编写，因为无关的变化而变得脆弱，难以维护，也难以做到目标无关。在"正确层次"的 IR 上执行变换使代码的分析和变换变得更容易，并且可以通过减小 IR 的大小并消除本来需要考虑的可能性来加快速度。

这就是我们首先对 IR 引入多面体技术的原因：尽管我们的基础"CFG 函数"表示完全能够表达任何计算，但它"太"具有表达力了。多面体技术施加的限制（例如对仿射循环界和数组下标的限制）定义了一个封闭的代数，可以表示一系列有趣的变换及其组合，并且由于其简单性，我们可以更高效、更可靠地执行（例如）依赖分析。

这引出了本文所探讨的一个重要问题：鉴于我们正在引入一种冗余且受限的方式来表达代码和变换，究竟哪种形式最适合执行我们想要的分析和变换？

我们探索了两种不同的设计点，它们能够表达相同类别的仿射循环计算，但使用了不同的表示形式。这些形式在冗长性、变换便捷性和分析便捷性方面以有趣的方式进行权衡。

## 背景：传统多面体形式

我们首先讨论了使用传统多面体调度集+域表示的表示方式，例如考虑如下类 C 代码：

```c
  void simple_example(...) {
    for (int i = 0; i < N; ++i) {
      for (int j = 0; j < N; ++j) {
         float tmp = X[i,j]    // S1
         A[i,j] = tmp + 1      // S2
         B[i,j] = tmp * 42     // S3
       }
    }
  }
```

多面体表示不关心实际计算，因此我们在下面的讨论中将它们抽象为 S1/S2/S3。最初，我们计划用如下经典形式表示（语法细节并不重要，下面可能略有不准确）：

```mlir
  mlfunc @simple_example(... %N) {
    %tmp = call @S1(%X, %i, %j)
      domain: (0 <= %i < %N), (0 <= %j < %N)
      schedule: (i, j, 0)

    call @S2(%tmp, %A, %i, %j)
      domain: (0 <= %i < %N), (0 <= %j < %N)
      schedule: (i, j, 1)

    call @S3(%tmp, %B, %i, %j)
      domain: (0 <= %i < %N), (0 <= %j < %N)
      schedule: (i, j, 2)
  }
```

在这种设计中，mlfunc 是一个无序指令包，其执行顺序完全由其调度控制。

然而，我们最近一致认为，更显式的调度树表示更适合我们的需求，因为它暴露了重要的结构，使分析和优化更加高效，并且使 SSA 值的作用域更加明确。这引导我们走向如下形式的表示：

```mlir
  mlfunc @simple_example(... %N) {
    d0/d1 = mlspace
    for S1(d0), S2(d0), S3(d0) {
      for S1(d1), S2(d1), S3(d1) {

        %tmp = call @S1(%X, d0, d1)      ;; S1
          domain: (0 <= d0 < %N), (0 <= d1 < %N)

        call @S2(%tmp, %A, d0, d1)      ;; S2
          domain: (0 <= d0 < %N), (0 <= d1 < %N)

        call @S3(%tmp, %B, d0, d1)      ;; S3
          domain: (0 <= d0 < %N), (0 <= d1 < %N)
      }
    }
  }
```

这一变化使循环的嵌套结构成为表示的显式部分，并使循环内的词法顺序具有意义（消除了调度中的常量 0/1/2）。

在上面的例子中并不明显，但该表示允许一些有趣的特性，包括循环嵌套中的指令具有不相等域的能力，如下所示——第二条指令忽略循环内部的外侧 10 个点：

```mlir
  mlfunc @reduced_domain_example(... %N) {
    d0/d1 = mlspace
    for S1(d0), S2(d0) {
      for S1(d1), S2(d1) {
        %tmp = call @S1(%X, d0, d1)    ;; S1
          domain: (0 <= d0 < %N), (0 <= d1 < %N)

        call @S2(%tmp, %A, d0, d1)      ;; S2
          domain: (10 <= d0 < %N-10), (10 <= d1 < %N-10)
      }
    }
  }
```

它还允许在指令内进行调度重映射，就像这个通过对两条指令的调度进行简单更改来引入对角斜切的例子：

```mlir
  mlfunc @skewed_domain_example(... %N) {
    d0/d1 = mlspace
    for S1(d0), S2(d0+d1) {
      for S1(d0+d1), S2(d1) {
        %tmp = call @S1(%X, d0, d1)    ;; S1
          domain: (0 <= d0 < %N), (0 <= d1 < %N)

        call @S2(%tmp, %A, d0, d1)      ;; S2
          domain: (0 <= d0 < %N), (0 <= d1 < %N)
      }
    }
  }
```

这种形式具有很强的表达能力，多面体代码生成器（将 mlfunc 降低到 cfgfunc 表示）处理这种能力，使引入循环变换的操作不必显式地操作循环结构。

## 提案：简化多面体形式

本文提出并探索了更进一步的想法，将所有域和调度信息移入"调度树"。在这种形式中，我们将有一种表示，其中给定 for 循环内的所有指令已知具有相同的域，该域由循环维护。在简化形式中，我们还有一个"if"指令，接受仿射条件。

我们上面的简单例子将表示为：

```mlir
  mlfunc @simple_example(... %N) {
    affine.for %i = 0 ... %N step 1 {
      affine.for %j = 0 ... %N step 1 {
        // identity noop in this case, but can exist in general.
        %0,%1 = affine.apply #57(%i, %j)

        %tmp = call @S1(%X, %0, %1)

        call @S2(%tmp, %A, %0, %1)

        call @S3(%tmp, %B, %0, %1)
      }
    }
  }
```

域缩减的例子将用 if 指令表示：

```mlir
  mlfunc @reduced_domain_example(... %N) {
    affine.for %i = 0 ... %N step 1 {
      affine.for %j = 0 ... %N step 1 {
        // identity noop in this case, but can exist in general.
        %0,%1 = affinecall #57(%i, %j)

        %tmp = call @S1(%X, %0, %1)

        if (10 <= %i < %N-10), (10 <= %j < %N-10) {

          %2,%3 = affine.apply(%i, %j)    // identity noop in this case

          call @S2(%tmp, %A, %2, %3)
        }
      }
    }
  }
```

这些 IR 表示完全相同的信息，使用相似的信息密度。"传统"形式引入了额外的抽象层次（调度和域），使指令的变换变得容易，但代价是使推理代码生成后这些指令将如何呈现变得困难。使用简化形式时，变换必须在其变换过程中内联执行代码生成的部分：要实现斜切，你不是简单地将调度改为 **(i+j, j)**，而必须显式生成如下代码（可能通过将多面体代码生成实现为变换调用的库来实现）：

```mlir
mlfunc @skewed_domain_example(... %N) {
  affine.for %t1 = 0 ... 2*N-2 step 1 {
    affine.for %t2 = max(0, t1-N+1) ... min(N, t1) step 1 {
      (%i, %j) = (%t1-%t2, %t2)
      ...
    }
  }
}
```

## 评估

这两种形式都能够表达相同类别的计算：具有仿射循环界和仿射内存引用的多维循环嵌套。尽管如此，它们在其他方面提出了非常不同的权衡取舍。

### 共同点：能够表达相同的计算

这两者都能表达相同类型的计算，例如用一种形式编写的核心可以在所有情况下用另一种形式表示。

### 共同点：依赖分析

这两种表示都使用仿射函数进行数据布局映射和访问下标，依赖分析的工作方式相同。

### 共同点：确定最优变换序列的难度

这类代码性能优化的一个主要挑战是选择所应用的各种循环变换的顺序和行为。每个决策都有非局部效应，两种表示都无助于解决这个本质上困难的问题。

### 共同点：IR 的紧凑性

在与我们最相关的情况下（超矩形空间），这两种形式是直接等价的：具有有限域的传统指令（例如上面的"reduced_domain_example"）最终在其循环内有一层 ML 的"if"。简化形式通过消除 IR 中的调度和域来为此付出代价。两种形式都允许通过代码复制来减少 IR 中的动态分支：传统方法允许指令分裂，简化形式支持指令复制。

重要的是要指出，在极端情况下传统形式在紧凑性方面获胜：例如循环斜切情况。这些情况在我们的工作负载中实践中很少见，而且恰好是下游变换希望对其正在做的事情保持显式的那些情况。

### 代码生成的简单性

mlfunc 的一个关键最终阶段是将其转换为 CFG 函数，这是降低到目标机器的必要部分。简化形式在这里具有明显优势：IR 与生成代码的结构直接对应。

相比之下，传统形式在降低到 CFG 函数的过程中具有显著的复杂性，因为 IR 中未包含的冗长性需要在代码生成期间出现。来自 ISL 的代码生成表明这是可能的，但这是一个非平凡的变换。

### 变换的便捷性

传统形式的一个优势是，对其执行某些变换更容易：斜切和分块只是对相关指令调度的变换，不需要更改循环结构。

实践中，简化形式要求将代码生成的复杂性移入变换本身——这有时是微不足道的，有时则比较复杂。作者认为，通过将代码生成算法本身作为变换调用的库函数，而不是在 mlfunc 处理结束时发生的不透明块，这应该是可能的。

此外，XLA 今天执行的那类变换（包括分块、填充、展开和其他矩形变换）在任何一种表示上都应该足够容易实现。唯一具有挑战性的情况是更高级的情况，例如斜切，例如用于 DMA 数据移动生成。

### 分析的便捷性：代价模型

简化形式对于分析和变换构建代价模型来说要容易得多（例如回答"在这个层次上展开循环会造成多少代码膨胀？"这类问题），因为更容易预测将生成哪些目标代码。使用传统形式时，这些分析必须预期多面体代码生成将对所考虑的一组指令做什么：在有趣的情况下（见"代码生成的代价"）这是非平凡的。

### 代码生成的代价

最先进的多面体代码生成[昂贵且复杂](https://lirias.kuleuven.be/bitstream/123456789/497238/1/toplas-astgen.pdf)，有时具有指数级时间复杂度。我们预期大多数机器学习工作负载将是超矩形的，因此在重要情况下应该可以进行专门化。也就是说，传统的多面体表示使引入复杂且昂贵的调度变得非常容易，并且没有提供理解和预测使用它们的代价模型的方法。IR 的所有下游客户端都需要准备好处理可能来自于它们的完整 IR 通用性。

简化形式定义了这一点：IR 中的概念保持简单，代码更直接地反映了降低到 CFG 函数和机器代码的代价模型。这对于加速器代码生成器的后期阶段预计非常重要。

### ML 函数中的 SSA

我们已经一致认为，mlfunc 中定义的值可以包含标量值，并且它们是基于传统支配关系定义的。在简化形式中，这非常简单：for 循环中定义的参数和归纳变量在其词法体内有效，而线性指令序列与基本块具有相同的"自顶向下"支配关系。

然而在传统形式中，情况并非如此：似乎需要大量关于代码生成将如何发射代码的知识，才能确定 SSA 形式是否正确。例如，以下是无效代码：

```mlir
  %tmp = call @S1(%X, %0, %1)
    domain: (10 <= %i < %N), (0 <= %j < %N)
    schedule: (i, j)

  call @S2(%tmp, %A, %0, %1)
    domain: (0 <= %i < %N), (0 <= %j < %N)
    schedule: (i, j)
```

因为 `%tmp` 在 %i 循环的某些迭代中未被定义。

这很重要，因为它使校验器更加复杂，但更重要的是，这意味着产生 SSA 形式的加载提升和其他优化将需要意识到这一点，并能够模拟代码生成的行为。

由此产生的一个涌现属性是，mlfunc 中的 PHI 节点（如果我们支持它们）也将必须具有域。

### IR 中缺乏冗余

传统形式对于相同类型的行为有多种编码：最终会在 `affine.for` 循环上有位来指定代码生成是否应使用"原子/分离"策略、展开循环等。指令可以被分裂，或者因为重叠域而生成其指令的多个副本，等等。

这对分析和代价模型来说是个问题，因为它们各自必须推理 IR 中这些额外的形式。

### 适合目的：降低到机器代码

这项工作的主要驱动力之一是降低到低级加速器代码，包括二维向量化、DMA 插入以及矩阵加速器单元的其他利用。在作者看来，传统形式额外的紧凑性对于这个目的来说是个负面因素：推理生成的机器代码将需要理解从 mlfunc 到降低代码的映射，这意味着它必须理解代码生成将做什么。

在简化形式中，"代码生成"的效果从 IR 本身始终是显而易见的，这应该使向量化到目标指令以及我们需要执行的其他分析变得更容易。

## 第三种备选方案：两种不同层次的 mlfunc

一种混合备选方案是在我们的 IR 中同时支持 mlfunc 的传统形式和简化形式。

这些阶段可以如下所示，例如：

1.  早期性能变换可以在传统形式上进行。
1.  部分代码生成降低到简化形式。
1.  针对分块、向量化和其他不太受益于传统形式的 2D 变换的目标特定降低阶段可以运行。
1.  当所有指令都被替换为在目标上有效的指令时，可以进行最终的 cfg 函数代码生成。

虽然这是可能的，但不清楚什么能够证明这种方法的复杂性是合理的。除非有非常令人信服的理由，否则最好不要这样做。**更新：** 我们作为设计团队讨论了这一点，并一致认为这不是一个好的方向。
